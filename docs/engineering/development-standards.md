# 开发规范（AI 时代增量迭代版）

## 1. 目标与适用范围

本规范适用于知识库项目全体成员（产品、后端、前端、算法、测试、运维、数据工程）。
目标是建立“连续演进 + 版本闸门”的研发机制，在高频 AI 迭代下保持质量、可控和可回滚。

---

## 2. 核心研发原则

- 小版本持续交付：保留版本管理，但缩小版本范围，避免大瀑布发布。
- 文档分层治理：总 PRD/总 TD 稳定，Feature PRD/Feature TD 增量更新。
- 决策可追溯：关键技术决策必须 ADR 化。
- 代码文档同变更：行为、接口、数据结构变化必须同步更新文档。
- 指标驱动迭代：以 RAG 质量与业务提效指标作为迭代“进入/退出条件”。

---

## 3. 版本与迭代管理

### 3.1 版本策略

- 产品版本语义：`v0.x`（内部开发，不上线）、`v1.0`（首个生产发布）、`v1.x`（生产迭代）。
- API 版本：遵循 SemVer（破坏性变更升级主版本）。
- Prompt/策略版本：独立版本号，不绑定代码版本。

### 3.2 迭代节奏

- 采用双周迭代（建议），每个迭代必须定义：
  - 目标（要解决的问题）
  - 范围（本次明确交付的能力）
  - 指标（上线后如何验证）
  - 退出条件（不达标是否回滚或灰度）

### 3.3 版本闸门（Release Gate）

- 不满足以下条件不得进入正式发布：
  - CI 全绿（lint/test/build/security）
  - 核心链路 E2E 通过
  - RAG 核心指标不劣于上个稳定版本
  - 回滚方案已演练

---

## 4. 文档分层与维护责任

### 4.1 文档分层（必须同时存在）

- 总 PRD：长期目标、用户价值、范围边界。
- 总 TD：平台级架构、跨模块约束、非功能设计。
- Feature PRD/TD：面向单个功能的主文档（单一事实源）。
- ADR：关键技术决策与取舍记录。
- Iteration 文档：迭代执行计划、RFC、复盘。
- Release 文档：版本映射、发布门禁结果、发布记录。

### 4.2 目录约定

- `docs/product/`：总 PRD 与跨功能产品文档
- `docs/architecture/`：总 TD 与跨功能架构文档、ADR
- `docs/engineering/`：开发规范、流程规范、Runbook
- `docs/ai/`：Prompt、Agent 策略、评测规范
- `docs/features/<feature-id>/`：功能主文档（`prd.md`、`td.md`、`changelog.md`）
- `docs/iterations/<version>/`：迭代文档（`README.md`、`sprint-xx-plan.md`、`rfc-*.md`）
- `docs/releases/<version>/README.md`：发布映射与发布结果

### 4.3 文档维护规则

- 日常开发先在 `docs/iterations/` 记录方案与计划。
- 代码合并前，必须将最终结论回写到 `docs/features/`。
- `docs/releases/` 仅做映射与结果归档，不重复承载完整 PRD/TD。
- 影响平台级原则时，再同步更新总 PRD/总 TD。

### 4.4 文档更新触发条件

- 任一变更涉及以下内容，PR 必须同步更新文档：
  - 对外 API 契约
  - 数据模型/索引结构
  - 核心业务流程
  - 权限与安全策略
  - Prompt/路由策略

---

## 5. 仓库与工程结构规范

建议结构：
- `apps/web`：用户端与管理端
- `apps/api-gateway`：统一入口层
- `apps/services/*`：业务服务与 AI 服务
- `libs/contracts`：OpenAPI、事件 schema、Prompt schema
- `libs/common`：通用组件、错误码、中间件
- `infra`：部署与基础设施代码
- `docs`：全局、功能、迭代、发布文档

原则：
- 契约集中存放，禁止散落定义。
- 业务逻辑与基础设施解耦。
- 跨服务交互必须显式契约化。

---

## 6. 分支、提交与评审规范

- 主分支：`main`（始终可发布）
- 开发分支：`feature/*`、`fix/*`、`chore/*`
- 提交规范：Conventional Commits（`feat/fix/refactor/docs/test/chore`）

PR 必须满足：
- 关联需求或缺陷编号
- 说明变更范围和风险
- 勾选 `Doc Impact`（是否需要文档更新）
- 涉及架构决策时附 ADR 链接
- 至少 1 名 reviewer 审核通过

---

## 7. 代码与契约规范

### 7.1 通用

- UTF-8、LF、UTC 时间标准。
- 禁止硬编码密钥，统一密钥管理。
- 错误结构统一：`code/message/trace_id/details`。
- 关键日志字段统一：`trace_id/tenant_id/user_id/module`。

### 7.2 TypeScript/Python

- TypeScript：`strict=true`，避免 `any`。
- Python：统一使用 `3.11.x`，并要求类型注解、`ruff + black + mypy`。
- AI 链路函数必须拆分为检索、生成、后处理，禁止大函数混杂。

### 7.3 API 与事件契约

- API：OpenAPI-first
- 事件：Schema-first（JSON Schema/Avro）
- 破坏性变更必须升级版本并提供迁移说明

RAG 响应最小字段：
- `answer`
- `citations[]`
- `confidence`
- `grounded`
- `trace_id`

---

## 8. 数据、索引与迁移规范

- 数据库变更必须通过 migration。
- 索引升级采用“双写 + 切换 + 回滚”。
- 大规模重建索引必须具备灰度与进度观测。

版本字段规范：
- `doc_version`：文档内容版本
- `index_version`：索引版本
- `prompt_version`：提示词版本
- `strategy_version`：检索/路由策略版本

---

## 9. 测试、评测与实验规范

### 9.1 测试分层

- 单元测试：核心逻辑和规则引擎
- 集成测试：服务契约、DB、缓存、队列
- E2E：问答主链路、SOP 主链路

### 9.2 RAG 评测基线

- 召回质量：Recall@K、MRR/NDCG
- 生成质量：引用覆盖率、幻觉率、可执行性评分
- 业务指标：FRT、一次解决率、满意度

### 9.3 实验治理

- 检索策略、模型或 Prompt 变更必须做 A/B 对比。
- 未通过基线的实验不得全量上线。

---

## 10. 安全与合规规范

- 最小权限原则（账号、服务、数据访问）。
- 权限过滤前置到检索层，不得仅在展示层控制。
- 日志与导出必须脱敏。
- 审计日志必须可追溯且不可篡改。

---

## 11. AI Agent 工程规范

- Prompt 模板文件化、版本化，禁止硬编码长 Prompt。
- 模型调用必须具备超时、重试、熔断、降级。
- 低置信回答必须触发兜底（澄清/拒答/转人工）。
- 工具调用必须经过权限校验并记录调用轨迹。
- 线上策略发布采用灰度与可回滚机制。

---

## 12. 运维与事故处理

- 健康检查：`/health/live`、`/health/ready`
- 告警分级：P0/P1/P2
- 标准流程：发现 -> 止血 -> 定位 -> 修复 -> 复盘
- P0/P1 事故需在 48 小时内完成复盘并形成行动项

---

## 13. 与当前 PRD 路线对齐

- 阶段 1（可用版）：优先稳定交付混合检索与引用问答。
- 阶段 2（提效版）：优先闭环评测、检索路由、SOP 流程。
- 阶段 3（智能版）：优先 Agent 执行治理与策略中心化。

每个阶段均执行“迭代文档推进 -> 功能文档回写 -> 发布映射归档”的组合策略。

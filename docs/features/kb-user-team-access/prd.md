## 目标上线版本 v1.0

## 1. 背景与目标

### 1.1 背景
当前系统缺少稳定的用户、团队与知识库归属关系，导致后续权限控制、审计追踪和多团队协作无法落地。

### 1.2 目标
按最小可演进方案构建访问基础：
- User-Team 多对多关系
- KnowledgeBase 单 Team 归属
- 资源角色支持 `owner/editor/viewer`
- 团队成员默认继承团队归属知识库的访问权限

### 1.3 非目标（v0.x 不做）
- 复杂 ABAC（属性级策略）
- 跨团队审批流
- 企业 SSO/SCIM 深度集成
- 段落级权限（知识切片级）

---

## 2. 用户与场景

### 2.1 目标用户
- 团队创建者：创建团队并担任 `team_admin`
- 团队管理员：管理团队成员、管理团队知识库授权
- 团队成员：访问团队归属知识库

### 2.2 核心场景
- 场景 A：用户加入多个团队，并在不同团队拥有不同角色
- 场景 B：创建知识库时指定归属团队
- 场景 C：团队成员默认可访问本团队归属知识库
- 场景 D：通过知识库成员表处理例外授权（跨团队/临时/覆盖）

---

## 3. 需求范围

### 3.1 功能需求
1. 用户管理（MVP）
- 创建用户、查询用户
- 用户状态管理（active/inactive）

2. 团队管理
- 创建团队、查询团队
- 用户与团队关联（多对多）
- 团队成员角色（team_admin/member）

3. 知识库管理
- 创建知识库并绑定 `owner_team_id`
- 查询知识库及归属团队

4. 权限设计
- 团队成员默认继承团队归属知识库的 `viewer` 权限
- 知识库成员表仅用于例外授权（提升/降级/跨团队/临时）
- 读取知识库：owner/editor/viewer
- 修改知识库：owner/editor
- 删除知识库：仅 owner

5. 审计与追溯
- 记录授权变更（谁在何时赋予或修改何权限）

### 3.2 非功能需求
- 关键权限接口响应 P95 < 500ms
- 权限判定逻辑可单元测试覆盖 >= 80%

---

## 4. 验收标准

### 4.1 功能验收
- 用户可加入多个团队并查询生效角色
- 知识库创建时必须绑定团队
- 团队成员默认具备团队归属知识库的 `viewer` 访问
- `knowledge_base_memberships` 不存团队全量成员，仅存例外授权
- 越权访问返回统一错误

### 4.2 数据验收
- 核心关系表无孤儿数据
- 所有授权变更有审计记录

---

## 5. 里程碑建议

- M1：users/teams/team_memberships 基础能力
- M2：knowledge_bases + 例外授权 `knowledge_base_memberships`
- M3：权限判定中间层 + 审计

---

## 6. 风险与应对

- 风险：默认权限与例外权限冲突
  - 应对：定义明确优先级（例外授权 > 团队默认）
- 风险：后续跨团队共享扩展成本高
  - 应对：保留 `knowledge_base_memberships` 承载例外授权
